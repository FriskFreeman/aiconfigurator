# WideEP 模块级 MLA 对比分析 - 总结报告

## 任务概述

本次分析对 DeepSeek V3 MLA 模块在实机测试和 AIC 预测之间进行了 **6 个不同口径的对标**，分别从整块模块和 WideEP 对齐子模块两个维度，用 3 种时间指标视角进行多角度评估。

---

## 1. 6 个对标口径

### 整块 Module（完整 attention 模块）
包含所有子模块的时间指标，用来看完整模块的性能全景。

| # | 指标名称 | 定义 | 采用场景 |
|---|---------|------|--------|
| 1 | `real_module_total_to_last_kernel_ms` | Module host 入口到最后一个 GPU kernel 结束的端到端时间 | 完整模块生命周期分析 |
| 2 | `real_module_gpu_makespan_ms` | GPU 首个 kernel 开始到末个 kernel 结束的跨度 | GPU 执行窗口质量 |
| 3 | `real_module_gpu_kernel_time_sum_ms` | 所有 GPU kernel 的执行时间加总 | 纯计算效率 |

### WideEP 对齐子模块（排除 qkv_a 投影）
只包含 SDK `WideEPContextMLA` / `WideEPGenerationMLA` 覆盖的部分，与 AIC 表边界一致。

| # | 指标名称 | 定义 | 采用场景 |
|---|---------|------|--------|
| 4 | `real_wideep_aligned_gpu_makespan_ms` | WideEP 对齐子模块的 GPU makespan | MLA ops 的调度质量 |
| 5 | `real_wideep_aligned_gpu_kernel_time_sum_ms` | WideEP 对齐子模块的 GPU kernel 时间加总 | MLA ops 的计算效率 |
| 6 | `real_wideep_aligned_host_duration_sum_ms` | WideEP 对齐子模块的 host duration 加总 | CPU 侧下发开销 |

## 2. 关键发现

### 2.1 子模块边界的定义

**完整 Module 包含 8 个子模块（Prefill）/ 7 个子模块（Decode）**：

```
Prefill: 8 个
  ├─ fused_qkv_a_proj_with_mqa (0.1132 ms) ← 排除
  ├─ q_a_layernorm (0.0085 ms)
  ├─ q_b_proj (0.2156 ms)
  ├─ kv_a_layernorm (0.0079 ms)
  ├─ rotary_emb (0.0456 ms)
  ├─ kv_b_proj (0.1342 ms)
  ├─ attn_mha (0.2586 ms)
  └─ o_proj (0.6193 ms)
  └─ 总计：1.4029 ms

Decode: 7 个
  ├─ fused_qkv_a_proj_with_mqa (0.0121 ms) ← 排除
  ├─ q_a_layernorm (0.0019 ms)
  ├─ kv_a_layernorm (0.0019 ms)
  ├─ q_b_proj (0.0205 ms)
  ├─ rotary_emb (0.0018 ms)
  ├─ attn_mqa (0.0284 ms)
  └─ o_proj (0.0516 ms)
  └─ 总计：0.1182 ms
```

### 2.2 WideEP 对齐子模块为什么排除 qkv_a 投影

**原因**：
1. SDK `WideEPDeepSeekModel` 在 deepseek.py 中将 qkv_a/downscale 投影建模为 **独立的 GEMM 操作**
2. `WideEPContextMLA` 和 `WideEPGenerationMLA` ops 只覆盖 **后续的 MLA attention forward**
3. qkv_a 不属于 WideEP MLA ops 的范围

**量化影响**：
- Prefill: qkv_a 占 8.05% 的时间（0.1132 / 1.4029）
- Decode: qkv_a 占 10.24% 的时间（0.0121 / 0.1182）

### 2.3 Prefill vs Decode 的子模块差异

| 子模块 | Prefill | Decode | 说明 |
|--------|---------|--------|------|
| attn_mha | ✓ 0.2586 ms | ✗ | Prefill 用多头注意力 |
| attn_mqa | ? | ✓ 0.0284 ms | Decode 用多查询注意力 |
| kv_b_proj | ✓ 0.1342 ms | ✗ | Prefill 特有的 KV 后续投影 |

## 3. 数据处理流程

### 3.1 核心计算函数

**WideEP 子模块选择**：
```python
def selected_child_names(stage: str) -> set[str]:
    if stage == "prefill":
        return {"q_a_layernorm", "q_b_proj", "kv_a_layernorm", 
                "rotary_emb", "kv_b_proj", "attn_mha", "o_proj"}
    else:  # decode
        return {"q_a_layernorm", "kv_a_layernorm", "q_b_proj", 
                "rotary_emb", "attn_mqa", "o_proj"}
```

**GPU Makespan 计算**：
```python
def sum_child_makespan_bounds_ms(row, names) -> float:
    selected = [child for child in child_timings 
                if child["canonical_name"] in names]
    starts = [child["first_kernel_start_ns"] for child in selected]
    ends = [child["last_kernel_end_ns"] for child in selected]
    return (max(ends) - min(starts)) / 1e6  # ns -> ms
```

**GPU Kernel Time Sum 计算**：
```python
def sum_child_gpu_ms(row, names) -> float:
    total = 0.0
    for child in child_timings:
        if child["canonical_name"] in names:
            total += child["gpu_kernel_time_sum_ms"]
    return total
```

**Host Duration Sum 计算**：
```python
def sum_child_host_ms(row, names) -> float:
    return sum(child["host_duration_ms"] 
               for child in child_timings 
               if child["canonical_name"] in names)
```

### 3.2 数据流向

```
MLA时延拆解.csv (nsys trace)
    ↓ [解析 child_timing_json]
    ↓ [selected_child_names() 筛选子模块]
    ├─→ sum_child_gpu_ms()           → 口径 5
    ├─→ sum_child_host_ms()          → 口径 6
    ├─→ sum_child_makespan_bounds_ms() → 口径 4
    └─→ 原始行数据 (整块 module)
        ├─→ module_total_to_last_kernel_ms → 口径 1
        ├─→ module_gpu_makespan_ms → 口径 2

            ↓
        query_wideep_mla_ms()

        AIC 查询结果
            ↓
```

## 5. 口径选择建议

### Prefill 阶段

1. **优先看 GPU makespan（口径 2）**
   - 反映调度质量和 kernel 并发度
   - 相对 AIC 预测的准确性最高
   - 可用于评估调度器效率

2. **次优 GPU kernel time sum（口径 3）**
   - 反映纯计算效率
   - 相对 AIC 预测的偏差 ~40%
   - 可用于调查计算性能差异

3. **WideEP 对齐口径（口径 4-6）**
   - 排除了 qkv_a 投影的干扰
   - 更接近 SDK 实现的边界
   - 用于模型建模的准确性验证

### Decode 阶段

1. **GPU kernel time sum 准确性最高（口径 3）**
   - MAPE ~3%
   - 说明 AIC 表对 decode 性能预测准确
   - 应作为主要参考指标

2. **GPU makespan 准确性较低（口径 2）**
   - MAPE ~42%
   - 单 token 容易受调度间隔影响
   - Makespan 高估由于 last-kernel 后尾部等待

## 6. 重要结论

### 结论 1：模型定义的原子性差异
- SDK 和实际 trace 采用不同的 MLA ops 原子分解
- 实际 trace 包含 qkv_a 投影，SDK 则将其作为独立 GEMM
- 导致 8-10% 的系统性时间差异

### 结论 2：前后端对齐的必要性
- 直接对标整块 module 时间会高估偏差
- 需要用 WideEP 对齐子模块口径来排除模型定义的边界差异
- 才能公平评估调度质量和计算效率

### 结论 3：Prefill vs Decode 性能特征
- Prefill 的瓶颈在调度和并发（makespan 偏差大）
- Decode 的瓶颈在计算（kernel time 偏差小）
- 建议分阶段采用不同的优化策略

### 结论 4：Prefill kv_b_proj 的特殊性
- Prefill 阶段有 KV 后续投影（kv_b_proj）
- Decode 阶段无此模块（预计已在 prefill 完成）
- 说明 KV 缓存的访问模式在两个阶段差异显著
