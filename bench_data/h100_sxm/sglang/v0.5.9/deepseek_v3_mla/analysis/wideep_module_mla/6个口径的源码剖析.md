# WideEP 模块级 MLA 对比 6 个口径的源码剖析

## 1. 总体架构

对比任务将整块 attention module 的时间指标分解为两个维度：
- **整块 module**：包含完整 attention module 的所有子组件
- **WideEP 对齐子模块**：SDK `WideEPContextMLA` / `WideEPGenerationMLA` 实际涵盖的部分（排除 qkv_a 投影）

每个维度提供 3 个不同的时间指标视角：
1. GPU kernel 时间加总
2. GPU makespan（从首个 kernel 开始到末个 kernel 结束）
3. Host duration 加总（仅对 WideEP 对齐维度）

## 2. 6 个口径的详细定义

### 口径 1：real_module_total_to_last_kernel_ms
**定义**：module host 入口到最后一个关联 GPU kernel 结束的端到端时间

**源数据路径**：来自 nsys 原始 trace CSV
```python
"real_module_total_to_last_kernel_ms": float(row.get("module_total_to_last_kernel_ms") or 0.0)
```

**计算方式**（在原始 trace 中）：
```
module_total_to_last_kernel_ns = module_last_kernel_end_ns - module_host_start_ns
```

**物理含义**：
- Host 函数入口的 timestamp
- 减去 GPU 端最后一个 kernel 完成的 timestamp
- 捕捉的是整个 module 的包括调度、执行、结束的完整生命周期

**涵盖范围**：全部 8 个子模块（prefill）或 7 个子模块（decode）

---

### 口径 2：real_module_gpu_makespan_ms
**定义**：module 内 GPU 首个 kernel 开始到末个 kernel 结束的跨度

**源数据路径**：来自 nsys 原始 trace CSV
```python
"real_module_gpu_makespan_ms": float(row.get("module_gpu_makespan_ms") or 0.0)
```

**计算方式**（在原始 trace 中）：
```
module_gpu_makespan_ns = module_last_kernel_end_ns - module_first_kernel_start_ns
```

**物理含义**：
- 纯 GPU 执行的跨度
- 不包含 host-to-first-kernel 的调度延迟
- 不包含 last-kernel-end 到 module-end 的尾部间隔（如果有）

**涵盖范围**：全部 8 个子模块（prefill）或 7 个子模块（decode）的所有 GPU kernel

---

### 口径 3：real_module_gpu_kernel_time_sum_ms
**定义**：module 内所有 GPU kernel 的执行时间加总

**源数据路径**：来自 nsys 原始 trace CSV
```python
"real_module_gpu_kernel_time_sum_ms": float(row.get("module_gpu_kernel_time_sum_ms") or 0.0)
```

**计算方式**（在原始 trace 中）：
```
module_gpu_kernel_time_sum_ns = sum(kernel.duration_ns for kernel in all_kernels)
```

**物理含义**：
- 每个 GPU kernel 实际执行的时间求和
- 不包含 kernel 之间的间隔或切换开销
- 等于所有 kernel 的 duration 累加

**涵盖范围**：全部 8 个子模块（prefill）或 7 个子模块（decode）的所有 kernel

---

### 口径 4：real_wideep_aligned_gpu_makespan_ms
**定义**：排除 qkv_a 投影后，WideEP 对齐子模块的 GPU makespan

**源数据计算过程**：
```python
# 选择 WideEP 对齐的子模块
names = selected_child_names(stage)  # stage = "prefill" 或 "decode"

# 计算只包含这些子模块的 makespan
def sum_child_makespan_bounds_ms(row, names):
    selected = [child for child in child_timings(row) 
                if child.get("canonical_name") in names]
    starts = [child.get("first_kernel_start_ns") 
              for child in selected 
              if child.get("first_kernel_start_ns") is not None]
    ends = [child.get("last_kernel_end_ns") 
            for child in selected 
            if child.get("last_kernel_end_ns") is not None]
    if not starts or not ends:
        return None
    return (max(ends) - min(starts)) / 1e6
```

**WideEP 对齐子模块集合**：

**Prefill 阶段**（8 个子模块 → 选 7 个）：
- ✓ `q_a_layernorm`
- ✓ `q_b_proj`
- ✓ `kv_a_layernorm`
- ✓ `rotary_emb`
- ✓ `kv_b_proj`
- ✓ `attn_mha`
- ✓ `o_proj`
- ✗ **`fused_qkv_a_proj_with_mqa`** ← **排除**

**Decode 阶段**（7 个子模块 → 选 6 个）：
- ✓ `q_a_layernorm`
- ✓ `kv_a_layernorm`
- ✓ `q_b_proj`
- ✓ `rotary_emb`
- ✓ `attn_mqa`
- ✓ `o_proj`
- ✗ **`fused_qkv_a_proj_with_mqa`** ← **排除**
- ✗ `kv_b_proj`（decode 中无此模块）

**物理含义**：
- 从首个选中子模块的首个 kernel 开始
- 到末个选中子模块的末个 kernel 结束
- 的 GPU 执行跨度

**排除 qkv_a 的原因**：
- SDK `WideEPDeepSeekModel` 在 deepseek.py 中将 qkv_a/downscale 投影建模为独立的 GEMM 操作
- `WideEPContextMLA` 和 `WideEPGenerationMLA` ops 只覆盖后续的 MLA attention forward（q/kv 后续投影、attention、o_proj）
- qkv_a 不属于 WideEP MLA ops 的范围，应单独建模

---

### 口径 5：real_wideep_aligned_gpu_kernel_time_sum_ms
**定义**：排除 qkv_a 投影后，WideEP 对齐子模块的所有 GPU kernel 时间加总

**源数据计算过程**：
```python
def sum_child_gpu_ms(row, names):
    total = 0.0
    count = 0
    for child in child_timings(row):
        if child.get("canonical_name") in names:
            total += float(child.get("gpu_kernel_time_sum_ms") or 0.0)
            count += int(child.get("gpu_kernel_count") or 0)
    return total, count
```

**子模块范围**：同口径 4（排除 qkv_a，其他子模块全选）

**物理含义**：
- 只加总 WideEP 对齐子模块内的 GPU kernel 时间
- 不包含 qkv_a 投影的 kernel 时间

---

### 口径 6：real_wideep_aligned_host_duration_sum_ms
**定义**：排除 qkv_a 投影后，WideEP 对齐子模块的 host 函数持续时间加总

**源数据计算过程**：
```python
def sum_child_host_ms(row, names):
    return sum(
        float(child.get("host_duration_ms") or 0.0)
        for child in child_timings(row)
        if child.get("canonical_name") in names
    )
```

**子模块范围**：同口径 4 和 5（排除 qkv_a）

**物理含义**：
- 各个 WideEP 对齐子模块在 CPU 侧的执行时间求和
- 包含 host-side 的 kernel 下发、数据准备、同步等开销
- 每个子模块的 host duration = host_end - host_start

| q_a_layernorm | ✓ 包含 | 0.0085 | Q 分支 layernorm |
| q_b_proj | ✓ 包含 | 0.2156 | Q 后续投影 |
| kv_a_layernorm | ✓ 包含 | 0.0079 | KV 分支 layernorm |

## 5. 源码调用链

对比数据从原始 trace CSV 到最终对比表的处理流程：

```
MLA时延拆解.csv (nsys trace)
    ↓ child_timings() 解析 child_timing_json
    ↓ selected_child_names(stage) 选择子模块
    ↓
    ├─ sum_child_gpu_ms()           → real_wideep_aligned_gpu_kernel_time_sum_ms
    ├─ sum_child_host_ms()          → real_wideep_aligned_host_duration_sum_ms
    ├─ sum_child_makespan_bounds_ms() → real_wideep_aligned_gpu_makespan_ms
    │
    └─ 原始行数据 (整块 module 列)
        ├─ module_total_to_last_kernel_ms → real_module_total_to_last_kernel_ms
        ├─ module_gpu_makespan_ms        → real_module_gpu_makespan_ms
        └─ module_gpu_kernel_time_sum_ms → real_module_gpu_kernel_time_sum_ms

query_wideep_mla_ms() 查 AIC 表
    ↓
aic_wideep_mla_latency_ms
```

## 6. 为什么需要 WideEP 对齐子模块口径

### 问题背景

1. **模型建模的原子性差异**：
   - 完整 nsys trace 的 module 包含 qkv_a 投影
   - SDK `WideEPDeepSeekModel` 将 qkv_a 作为单独 GEMM，不在 WideEP MLA ops 中
   
2. **AIC 查表的边界**：
   - `query_wideep_context_mla()` 和 `query_wideep_generation_mla()` 只包含 MLA attention 的部分
   - 不包含上游的 qkv_a 投影

3. **公平对比的需要**：
   - 如果直接对比整块 module 时间 vs AIC 查询结果，会有系统性高估（多了 qkv_a）
   - WideEP 对齐子模块口径排除了这个偏差源

### 具体例子

Prefill 时，完整 module 总时间 1.4029 ms，其中：
- qkv_a 投影：0.1132 ms
- **实际 MLA ops 部分**：1.2897 ms ← **应与 AIC 对比的是这部分**

如果用整块 module 时间去对标 AIC 结果，会被 qkv_a 的 0.1132 ms 拉高，造成虚假的"高估"。

## 7. 端到端对齐验证

### Prefill 口径选择建议

1. **看模块级效率**：用 `real_module_gpu_kernel_time_sum_ms` 和 AIC 对比
   - 直观展示 GPU kernel 执行效率
   - MAPE: ~40% （见原报告）

2. **看调度质量**：用 `real_module_gpu_makespan_ms` 和 AIC 对比
   - 反映 kernel 并发度、调度间隔的综合效果
   - MAPE: ~16% （见原报告，更接近）

3. **对齐 SDK 实现**：用 `real_wideep_aligned_gpu_kernel_time_sum_ms` 和 AIC 对比
   - 排除了模型定义边界的差异
   - MAPE: ~49% （见原报告）

### Decode 口径选择建议

1. **Decode 的 GPU kernel sum 非常接近** MAPE ~3%
   - 说明 AIC 表对 decode 性能预测准确
   - 建议优先看 `real_module_gpu_kernel_time_sum_ms`

2. **Makespan 准确性较低** MAPE ~42%
   - Decode 单 token 很容易受调度间隔影响
   - Makespan 高估由于 last-kernel 后有尾部等待

## 8. 总结

**6 个口径的逻辑**：

| 口径 | 范围 | 时间类型 | 用途 |
|------|------|----------|------|
| real_module_total_to_last_kernel_ms | 整块 | 端到端 | 完整 module 生命周期 |
| real_module_gpu_makespan_ms | 整块 | GPU 跨度 | GPU 执行窗口大小 |
| real_module_gpu_kernel_time_sum_ms | 整块 | GPU 加总 | 纯 GPU kernel 执行时间 |
| real_wideep_aligned_gpu_makespan_ms | WideEP 对齐 | GPU 跨度 | MLA ops 的 GPU 执行窗口 |
| real_wideep_aligned_gpu_kernel_time_sum_ms | WideEP 对齐 | GPU 加总 | MLA ops 的纯 GPU 时间 |
| real_wideep_aligned_host_duration_sum_ms | WideEP 对齐 | Host 加总 | MLA ops 的 CPU 下发开销 |

**关键区别**：
- **整块 vs WideEP 对齐**：排除 qkv_a 投影（~8-10% 时间差）
- **GPU makespan vs kernel sum**：后者是累加，前者是跨度（反映并发度）
- **Host duration**：只对 WideEP 对齐维度提供，反映 CPU 侧开销
