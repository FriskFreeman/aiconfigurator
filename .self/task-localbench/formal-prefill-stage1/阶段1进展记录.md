  - `20260610_104304_*`

- 原生 SGLang split

### prefix_len信息来源

当前没有依赖 SGLang 内部进程直接回传 prefix 信息。曾尝试在 `Scheduler.run_batch()` 外层 monkey patch NVTX marker，但 Engine 的 scheduler 子进程没有稳定继承该 patch，因此最终采用更稳的离线重建方式。

具体入口和方法是：

- nsys 导出阶段进入 `export_nsys_profile.py`。
- `build_mla_aligned_summary()` 读取 `report.sqlite` 中的 NVTX marker，定位 `model.model.layers.X.self_attn`。
- `_extract_shape_info()` 从 `attn_mha/attn_mqa` 子模块 NVTX payload 中读取 attention 输入形状。
- `_load_run_meta()` 读取运行时生成的 `run_meta.json`，获得 `prompt_lens`。
- `_load_engine_kwargs()` 读取 `engine_kwargs.json`，获得或回退 `chunked_prefill_size=8192`、`max_prefill_tokens=16384`。
- `_reconstruct_prefill_rounds()` 按 SGLang `PrefillAdder` 的核心规则重建每轮 prefill batch。
- `_merge_scheduler_chunk_info()` 把重建结果写入 `shape_info`，包括 `current_chunked_req_prefix_len`、`chunked_req_prefix_lens`、`aggregate_prefix_len`、`aggregate_extend_len`、`aggregate_seq_len_after` 和 `reconstructed_prefill_round`。

因此现在的 `prefix_len` 不是简单从 `total_tokens - token_count` 得出，而是优先来自重建的 scheduler 行为，字段来源标记为：

- `current_chunked_req_prefix_len_source = reconstructed_scheduler`

### 为什么不能只依赖attention输入形状

简单场景下，`attn_mha` 的输入形状经常可以用：

- `prefix_len = total_tokens - token_count`

例如单请求 `prompt_len=16384` 会形成：

- 第1块：`token_count=8192, total_tokens=8192, prefix=0`
- 第2块：`token_count=8192, total_tokens=16384, prefix=8192`

但异构 batch 和 mixed/chunk 场景可能走 `attn_mqa` 路径，此时 attention 输入形状的第二、第三个 tensor 不再表达同样的总上下文语义，单靠 `total_tokens - token_count` 会错误地得到 0。

### 已验证的变长样例

样例一：

- 输入 prompt_lens：`4096,16384,8192`
- 运行目录：`20260615_102443_prefill_stage1_verify_var_4096_16384_8192_*`
- 重建结果与 trace 形状一致：
  - instance 1：`4096/4096, prefix=0`
  - instance 2：`8192/8192, prefix=0`
  - instance 3：`8192/16384, prefix=8192`
  - instance 4：`8192/8192, prefix=0`

样例二：

- 输入 prompt_lens：`1024,8192,4096,8192`
- 运行目录：`20260615_104055_prefill_stage1_verify_var_1024_8192_4096_8192_*`
- 该样例触发了更复杂的混合 batch：
  - round 1：req0 `1024` + req1 前 `7168`，`current_chunked_req_prefix_len=0`
  - round 2：req1 剩余 `1024` + req2 `4096` + req3 前 `3072`，`chunked_req_prefix_lens=[7168,0]`，`current_chunked_req_prefix_len=7168`
  - round 3：req3 剩余 `5120`，`current_chunked_req_prefix_len=3072`

这个样例证明，`attn_mqa` 路径下必须使用调度重建信息，不能只用 attention 输入形状推断 prefix。

### 当前结论

- 对 single request 或简单 `attn_mha` 场景，attention 输入形状可以作为 sanity check。
- 对异构 batch、mixed chunk、`attn_mqa` 场景，正式分析应以 `reconstructed_scheduler` 字段为准。
- `MLA对齐解析.json` 中的 `shape_info.reconstructed_prefill_round.items` 是当前最完整的 per-request 粒度信息，包含 `req_id/extend_len/prefix_len/seq_len_after/prompt_len/is_chunked_req`。
- 后续做实机-AIC 对比时，应优先读取 `current_chunked_req_prefix_len_source`，若为 `reconstructed_scheduler`，则使用重建字段；若只有 `attention_inputs`，则说明当前运行缺少足够的调度上下文，只适合作为简单场景参考。

### 附注：prefix_len重建的有效性与风险

当前 `prefix_len` 解析可以理解为“trace 锚定 + scheduler 核心逻辑重放”：

- trace 负责给出真实发生过的 `self_attn` 实例、执行顺序、子模块边界和 attention 输入形状。
- `run_meta.json / engine_kwargs.json` 负责给出请求长度、batch 顺序、`chunked_prefill_size`、`max_prefill_tokens` 等调度输入。
- `_reconstruct_prefill_rounds()` 按 SGLang `PrefillAdder / _get_new_batch_prefill_raw` 的核心 token budget 逻辑，重放每轮 prefill 中哪些请求进入 batch、哪些请求被切成 chunk、每个 chunk 前已有多少 prefix。

因此，在当前阶段1受控条件下，这个方法是有效的：

- offline Engine 执行。
- prompt 在脚本中一次性构造，顺序可知。
- `schedule_policy=fcfs`。
- `disable_radix_cache=True`，没有 radix/prefix cache 命中。
- 不启用 HiCache、LMCache、storage prefetch 等外部 KV/前缀缓存。
- 不启用 PD disaggregation、LoRA、priority scheduling、prefill delayer、dynamic chunking。
- 当前关注纯 prefill，没有与已有 decode batch 的复杂混排。
- 主要参数保持 H100/SGLang v0.5.9 默认语义：`chunked_prefill_size=8192`、`max_prefill_tokens=16384`，除非 run 的 `engine_kwargs.json` 明确记录了覆盖值。

但它不是完整 SGLang Scheduler 的逐行模拟。以下场景可能导致 `reconstructed_scheduler` 失效或只能作为近似参考：

- 开启 radix cache、chunked prefix cache、HiCache、LMCache、host/storage cache hit 时，真实 `prefix_indices / extend_input_len / host_hit_length` 会被 cache 命中改写，脚本仅凭原始 prompt 长度无法还原。
- 设置 `prefill_max_requests`、`max_running_requests`、priority scheduling、preemption、prefill delayer 后，请求进入 batch 的顺序和数量可能不再等价于当前 FCFS token-budget 重放。
- 开启 `enable_dynamic_chunking`、更复杂的 `enable_mixed_chunk`、overlap scheduling、two-batch/single-batch overlap，或者 prefill 与 decode 已在同一 scheduler 周期混排时，当前简化逻辑可能漏掉 decode token budget、running batch 约束和动态 chunk 调整。
- 使用 LoRA、multimodal、speculative、disaggregation/PD、context parallel、pipeline parallel、DP attention 等模式时，真实 batch 组织可能受额外约束影响。
- 如果请求构造顺序与 scheduler 实际接收顺序不同，或 tokenizer/截断/对齐逻辑改变了真实输入 token 数，重建也会偏离。

结论：

- 对当前阶段1实验目录中的受控 run，`current_chunked_req_prefix_len_source=reconstructed_scheduler` 可以作为正式分析字段使用。
- 对后续更复杂配置，建议优先增加真正的 scheduler-side 元数据输出，例如在 SGLang scheduler 进程内写日志或 NVTX payload，而不是继续扩大离线重建逻辑的假设范围。

## 2026-06-17补充：单卡 TP 形状对齐实现

本轮补充了阶段1所需的单卡 `TP shape-only` 能力，目标不是在单卡上真实复刻 SGLang 的多卡 TP runtime，而是：

- 在单卡、Engine、dummy model 路径下
- 让 `DeepSeek-V3` 的 MLA 模块按某个 TP rank 的本地 shard 形状执行
- 只观察 rank0 的本地计算
- 不引入 TP 通信

### 当前实现原理

当前实现本质上是一个 **Engine 外部的非侵入式 shape override**。

不是去修改 SGLang 内部真实的 TP 调度、NCCL group 或多进程执行，而是在运行前生成 `local_model/config.json` 时，直接把模型配置中的 TP 相关头数改成 rank0 shard 后的本地形状，再交给 SGLang 正常加载。

具体做法位于：

- `.self/task-localbench/formal-prefill-stage1/run_formal_prefill_stage1.py`

在 `build_local_model(...)` 中：

- 读取 `src/aiconfigurator/model_configs/deepseek-ai--DeepSeek-V3_config.json`
- 当 `tp_size > 1` 时，将：
  - `num_attention_heads`
  - `num_key_value_heads`
  按 `tp_size` 做整除
- 并在生成的 `local_model/config.json` 中写入：
  - `_aic_tp_shape_only_rank0`

因此当前机制可以理解为：

- 对外部脚本而言，请求的是 `tp_size = K`
- 对 SGLang Engine 而言，仍然是在单卡、`tp_size=1` 的普通执行环境中运行
- 但它读取到的本地模型配置，已经是“等价于 TP rank0 本地 shard 后”的 attention 头数

这是一种 **shape-only / rank0-only / no-communication** 的取巧实现。

### 为什么不继续走 runtime monkey patch

本轮曾尝试过另一条路线：

- 在 `run_engine_inside_container.py` 中 monkey patch `_TP / _ATTN_TP` group
- 期望让 `ModelRunner.load_model()` 以及 attention forward 看到伪造的 `tp_size`

但从结果看，这种方法没有稳定进入 SGLang 的 scheduler / worker 子进程，最终表现为：

- run 本身可以成功
- 但 `MLA对齐解析.json` 中的头数与 projection 维度仍保持 TP=1 的全量形状

因此当前没有继续依赖这条 runtime patch 路线，而改用更稳的 config 形状改写方案。

- prefill `attn_mha`：`[[32, 128, 192], [32, 128, 192], [32, 128, 128]]`
- `q_b_proj.weight = [24576, 1536]`
- `kv_b_proj.weight = [32768, 512]`
- `o_proj` 输入为 `[32, 16384]`

因此可以确认：

- 当前方案不是“表面打了 tp=2 标签”
- 而是已经真实改变了 MLA 模块在单卡 Engine 路径中的 rank-local 头数与投影维度

### 适用性

该方法当前适用于：

- 阶段1对 MLA 模块内部单卡执行情况的观察
- 关注 rank0 本地 shard 的：
  - attention head 数
  - q/kv/o projection 维度
  - attention kernel 输入形状
  - module / kernel 级 trace breakdown

也就是说，它适合回答的问题是：

- “如果真实系统是 TP=2 / TP=4，那么单个 rank 上 MLA 的本地算子形状和局部执行大致是什么样？”

对于当前任务“主要看 MLA 模块内部单卡执行情况”，这是可接受且有效的。

### 局限与隐患

该方法不是完整 TP 仿真，边界需要明确。

1. 不是真实多卡 TP

- 没有真实 `tensor_model_parallel_all_reduce / all_gather / reduce_scatter`
- 没有 NCCL / custom all-reduce / 通信 overlap
- 不能代表真实多卡 TP 的端到端时延

2. 仅对齐了模型形状，不保证数值语义与真实 TP 完全等价

- 当前是把 head 数直接改成 rank-local 头数
- 对 MLA 内部形状是有效的
- 但不等于真实多 rank 下所有 hidden state / logits 的数学语义都被完整保留

3. 更接近“本地 shard 模型”而不是“完整模型的 rank0 视图”

- 由于是在 config 层面直接缩减 `num_attention_heads / num_key_value_heads`
- SGLang 会把它当作一个头数更少的本地模型来加载
- 因此它并不经过真实 TP runtime 对 full model 的切分与同步逻辑

4. 对非 MLA 模块的适用性需要单独判断

- 当前已验证的是 `DeepSeek-V3` 的 MLA 主链路
- 如果后续要分析 MoE、LM head 或更复杂的 TP/EP 交互模块
- 需要单独检查这种 config 级 shape override 是否仍然合理

5. 结果解释时必须显式标注

后续使用这类 run 做分析时，应明确写成：

- `tp_shape_only_rank0`
- 或“single-card TP rank0 shape-only run”

避免将其误解为：

- 真实多卡 TP 端到端结果
- 或完整的 TP runtime 行为复现

### 当前结论

当前这版 TP 实现可以概括为：

- **非侵入式**
- **Engine 外部 config 改写**
- **只做 rank0 本地 shard 形状对齐**
- **不含 TP 通信**

它不能替代真实多卡 TP，但对于当前阶段1任务中“只关心 MLA 模块内部单卡本地执行形状与时延”的目标，是一个足够实用、且已经验证跑通的方案。
